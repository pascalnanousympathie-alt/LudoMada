# Render Free — LudoMada staging (Railway replacement candidate)

## Scope and safety

This Blueprint creates a **new staging API** named `ludomada-api-staging` from this repository's Dockerfile. It does not modify/delete the existing Railway project, its Postgres volume, the Nanou Browser Render service, or the shared `mega-project-apps` service.

The target is Render Free in Singapore plus the existing Supabase Free project `ludomada-cloudflare-staging` (`jliatljqvvbibcibnrjk`, region `ap-south-1`). The Supabase database currently contains the 13 current LudoMada application tables with zero rows. **No Railway database data has been copied**; the old Railway service and database were observed offline, and their volume has not been inspected or deleted. Treat this only as a staging replacement until a data backup/export and explicit cutover plan exist.

## Required protected configuration

Render's initial Blueprint flow prompts for `DATABASE_URL` and `CORS_ORIGINS`. Enter secrets only in Render's protected Environment settings; do not put them in this repository, GitHub comments, or ChatGPT.

Use Supabase Dashboard → Connect → **Session pooler** (IPv4; port 5432) to obtain the exact host and connection details. Do not compose a hostname from the region: Supabase uses a pooler cluster index that must be copied from the Connect dialog.

A dedicated least-privilege PostgreSQL role named `ludomada_render_staging` has already been created in this target staging database. It is `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, and `NOCREATEROLE`; its database-connect, `public` schema usage, current table/sequence DML, and the five current application enum USAGE grants were verified. It deliberately has **no password yet**, so it cannot authenticate until the owner sets one directly.

**Required manual step:** open Supabase Dashboard → SQL Editor for `ludomada-cloudflare-staging` and execute the following with a new strong URL-safe password generated in a password manager. Do not send the password to ChatGPT or commit it anywhere:

```sql
ALTER ROLE ludomada_render_staging
  WITH PASSWORD 'REPLACE_WITH_A_NEW_RANDOM_URL_SAFE_PASSWORD';
```

The shared-pooler connection username must be `ludomada_render_staging.jliatljqvvbibcibnrjk`; URL-encode the password if necessary. The URL must use the **exact** pooler host copied from Supabase and port `5432`. Do not assume the pooler hostname from the region.

Set `DATABASE_URL` to the Supabase **session-pooler** URL using that role, e.g. `postgresql://ludomada_render_staging.jliatljqvvbibcibnrjk:<URL-ENCODED-PASSWORD>@<EXACT-POOLER-HOST>:5432/postgres?sslmode=require`. Replace the placeholder values locally in Render's protected settings only.

Set `CORS_ORIGINS` to the comma-separated, exact HTTPS origins of the intended client/web UI. `JWT_SECRET` is generated by Render. `PG_POOL_MAX=2` limits connections on the free instance. The MVola live/sandbox, Airtel sandbox, and Binance live payment switches are explicitly disabled in the Blueprint; Orange Money remains disabled in application code.

## Schema/migration gate — do not skip

The restored staging database already has the current 13-table schema, but it has no `public._prisma_migrations` table. The historical Prisma migration chain contains earlier schema states (including a `CREATED` game status not present in the current schema). Therefore, do **not** run `prisma migrate deploy` blindly against this existing schema: the old migrations may try to create objects that already exist.

Before any Prisma baseline work, follow [`docs/PRISMA_STAGING_BASELINE.md`](./PRISMA_STAGING_BASELINE.md): it requires a read-only schema diff, a zero-row check across every application table, a temporary `CREATE` grant that is revoked immediately after recording migration history, and explicit `prisma migrate resolve --applied` commands. The runtime role must not run future DDL migrations, and this Blueprint intentionally starts the application without mutating the schema.

## Release checks

1. Render build succeeds from the intended `main` commit and stays on the Free plan.
2. `GET /health` returns 200; `GET /ready` returns 200 only when the database connection succeeds.
3. Register/login and harmless game/lobby endpoints work using staging-only test accounts.
4. Confirm database errors don't disclose credentials; confirm JWT auth, CORS, request limits, and rate limits.
5. Run unit/integration/concurrency/security tests and staging-only load tests.
6. Confirm all live-payment switches remain false. Do not enable real MVola/Airtel/other payment paths as part of hosting setup.
7. Do not switch production Android clients or any custom domain to this API until owner-approved tests, backups/export, rollback, and payment/security review pass.

## Free-plan limitations

Render Free can sleep after idle time and has limited CPU/RAM. Supabase Free may pause after prolonged inactivity. This is for staging/evaluation, not a reliable production wallet or real-money service. Do not create paid resources or enable a paid IPv4 add-on to work around networking; use Supabase's included IPv4 session pooler.
